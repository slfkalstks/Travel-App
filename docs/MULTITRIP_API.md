# 현재 다중 여행 API·저장 계약

2026-11-01 현재 실행 코드의 `/api/demo` 계약이다. [시스템·데이터·API v2 설계](planning/02_시스템_데이터_API_설계.md)의 인증·PostgreSQL·오프라인 동기화 제안과 구분한다. 현재 서버는 로컬 단일 사용자·단일 프로세스 JSON 어댑터이며 인증·소유권 검사는 구현하지 않았다.

## 여행 API

| 메서드·경로 | 요청 | 성공 응답 |
|---|---|---|
| `GET /api/demo/trips` | 없음 | 보관된 여행을 포함한 `Trip[]`; 빈 목록은 `[]` |
| `POST /api/demo/trips` | 아래 7필드; 앱은 `Idempotency-Key` 전달 | 생성한 여행의 `Workspace` |
| `PATCH /api/demo/trips/{id}` | 아래 7필드 | 수정한 여행의 `Workspace` |
| `PATCH /api/demo/trips/{id}/archive` | `{"archived":true}` 또는 `false` | 해당 여행의 `Workspace` |
| `DELETE /api/demo/trips/{id}` | 없음 | 삭제 후 남은 `Trip[]` |
| `GET /api/demo/workspace` | 앱은 `X-Trip-Id` 전달 | 해당 여행의 `Workspace` |

생성·수정 필드는 `title`, `destination`, `country`, `startDate`, `endDate`, `travelers`, `budgetKrw`다. 생성 시 서버가 ID를 정하고 표지는 빈 문자열, 보관 여부는 `false`, 일정·준비물·경비·예약·장소·기록은 빈 목록으로 시작한다. 수정은 ID·표지·보관 상태·하위 자료를 유지한다.

이름은 120자, 도시/지역·국가는 각각 80자까지이며 공백만 있는 값은 거절한다. 날짜는 실제 존재하는 `YYYY-MM-DD`, 1900~2100년, 종료일 ≥ 시작일, 양 끝을 포함해 366일 이내다. 인원은 1~20명, 원화 예산은 정수 0~10억 원이다. 기간 수정으로 기존 일정이 기간 밖이 되거나 지출이 새 종료일 이후가 되면 저장을 거절한다. 출발 전 지출과 여행 기간 밖 기록은 허용한다. 예약은 여행 전후 이동·숙박도 저장하므로 기간 밖이어도 유지하고 조회한다. [예약 날짜 계약](RESERVATION_API.md)을 따른다.

삭제는 해당 여행의 일정·준비물·경비·예약·장소·기록을 함께 제거한다. 앱은 여행명·기간·삭제 영향을 확인한 뒤 요청한다. 같은 ID의 DELETE 재요청은 남은 목록을 반환하며 마지막 여행을 삭제한 뒤 서버를 다시 시작해도 예시 여행을 되살리지 않는다. 보관은 자료 삭제 없이 `archived`만 변경한다.

## 여행 지정·재시도

앱은 workspace 조회와 모든 일정·준비물·지출·장소·기록 변경에 `X-Trip-Id`를 보낸다. 여행 자체 수정·보관·삭제는 URL의 ID를 사용한다. 서버는 전역 선택 여행을 저장하지 않는다. 명시한 여행 ID가 없거나 빈 문자열이면 404다. 기존 호출 호환을 위해 **헤더 자체를 생략**하면 `trip-osaka-2026`, 없으면 저장된 첫 여행을 사용하며 목록이 비었으면 404다. 따라서 다중 여행 클라이언트는 헤더를 항상 지정해야 한다.

앱의 여행 생성과 하위 POST는 멱등성 키를 전달한다. 서버는 키와 요청 지문을 저장하고 같은 요청의 재전송은 중복 생성하지 않는다. 하위 작업의 키는 여행별로 분리되며, 여행 생성 키는 컬렉션에 저장한다. 키를 재사용하면서 본문이 달라지면 409다. 삭제된 여행의 생성 키를 재전송해도 여행이 부활하지 않고 409를 반환한다. 현재 서버 계약에서 멱등성 헤더는 선택 사항이므로 헤더를 생략하는 외부 호출의 중복 방지까지 보장하지 않는다.

## 저장 형식과 이전

최상위 `schemaVersion=2`, `workspaces[tripId]`, `creationReceipts`를 저장한다. 각 여행 항목은 기존 `workspace`와 여행별 `receipts`를 보존하며 내부 `schemaVersion=1` 표기도 유지한다. 이는 최상위 컬렉션 버전과 구분한다.

기존 단일 workspace/스키마 1 파일은 원본 바이트를 `*.pre-schema2-<UUID>.bak`으로 백업하고 컬렉션으로 감싼 뒤 임시 파일·flush·원자 교체로 저장한다. 변환 시 기존 하위 데이터와 멱등성 영수증을 보존하고 `archived`의 기본값만 `false`로 추가한다. 알 수 없는 버전·손상 JSON·여행 ID 불일치는 시작 단계에서 거절하며 원본을 덮어쓰지 않는다. JSON 파일이 처음부터 없을 때만 개발용 초기 여행을 생성한다.

[검증 기록](VERIFICATION.md)의 서버 9개·상태 8개 추가 테스트가 이 계약을 확인한다. PostgreSQL 연결·사용자 백업/복원·앱 로컬 DB/동기화의 증거로 해석하지 않는다.

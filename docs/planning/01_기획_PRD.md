# 개인 여행 공간 — 기획 및 PRD v2.0

작성일: 2026-11-01 · 상태: 앱 전환 설계 초안

최신 UI·항공권 수정사항: [모바일 UI 재설계](05_모바일_UI_재설계_및_항공권.md). 아래 장기 제품 요구사항 전체가 현재 구현 완료된 것은 아니다.

## 1. 제품 정의

개인 여행자가 여행을 탐색하고 준비하는 순간부터 현지 일정 진행, 비용 관리, 귀국 후 기록까지 한 여행 단위로 관리하는 Android·iOS 앱이다. 핵심 가치는 **필요한 여행 정보를 다시 찾는 시간을 줄이고, 연결이 불안정한 현지에서도 저장한 일정과 서류를 사용할 수 있게 하는 것**이다.

주 사용자는 기존 요구에 따라 소유자 한 명이다. 여러 기기 사용은 지원하도록 설계한다. 일반 사용자 대상 공개 서비스, 동행자 공동 편집, 커뮤니티는 확장 제안이며 현재 확정 요구사항은 아니다.

기존의 React 웹 중심 기획을 Kotlin Multiplatform 앱 중심으로 전환한다. Kotlin Multiplatform은 공통 데이터·업무 로직을 공유하고 Compose Multiplatform은 공통 화면을 담당한다. 백엔드는 Kotlin + Spring Boot, 중앙 DB는 PostgreSQL을 사용한다.

## 2. 해결하려는 문제와 검증할 가설

| 문제 가설 | 제품 대응 | 확인 방법 |
|---|---|---|
| 일정·예약 메일·PDF·지도·메모가 흩어져 필요한 정보를 다시 찾아야 한다 | 여행 상세 화면에서 연결 | 기존 방식과 앱에서 동일 예약서 찾기 시간 비교 |
| 출발 직전 예약·준비물 누락 여부를 파악하기 어렵다 | 마감일이 있는 체크리스트와 출발 준비 요약 | 여행 준비 시나리오에서 누락 항목 발견 여부 확인 |
| 외화 지출을 기록해도 예산과 비교하기 어렵다 | 원금액·통화·적용 환율을 보존한 지출 관리 | 환율 유무·여러 통화·환불 사례로 계산 확인 |
| 통신이 불안정하면 일정·예약서를 열기 어렵다 | 선택한 여행과 파일을 기기에 저장 | 비행기 모드에서 앱 종료 후 다시 열어 검증 |
| 여행이 끝난 뒤 기록과 실제 비용이 연결되지 않는다 | 일정·장소·지출에 연결된 여행 기록 | 여행 회고 화면에서 누락 없이 추적되는지 확인 |

이는 시장조사로 입증된 통계가 아닌 설계 가설이다. 실제 인터뷰·사용성 검증 결과를 추후 기록한다. 경쟁 서비스보다 우수하다는 주장은 현재 하지 않는다.

## 3. 대표 사용자 여정

1. 여행 이름·방문 도시·기간·기준 통화·예산을 등록한다.
2. 가고 싶은 장소와 숙소를 저장하고 날짜별 일정에 배치한다.
3. 직접 예약한 항공·숙소 내역과 PDF를 등록한다.
4. 준비물·예약 확인 목록과 마감일을 정한다.
5. 출발 전에 여행 정보와 필요한 파일을 기기에 다운로드한다.
6. 현지에서 오늘 일정과 예약서를 열고 지출·메모를 기록한다.
7. 연결이 회복되면 변경 내용을 서버와 동기화한다. 충돌이 있으면 두 내용을 비교한다.
8. 귀국 후 실제 지출·사진·장소를 모아 여행을 회고한다.

### 대표 시나리오

‘오사카 3박 4일’이라는 가상 시연 여행을 만든다. 항공편에는 출발·도착 공항의 시간대를 각각 입력하고 숙소에는 체크인 정보와 예약서를 연결한다. 현지에서는 네트워크 없이 예약서를 확인하고 엔화 지출을 입력한다. 귀국 후 재연결하여 다른 기기에서도 같은 기록을 확인한다. 사용자 화면에는 시연 배너를 넣지 않는다. 개발용 fixture의 출처와 현재 구현 범위는 개발 문서에 기록하며, 수동 계획을 실제 공급사 예약 확정이나 실시간 가격으로 소개하지 않는다.

### FR-06 지도 세부 정책

지역별 지도 제공자를 선택하며 여러 국가 여행에서는 현재 보고 있는 장소의 국가를 기준으로 한다. 지도 화면에 경로를 그렸다고 실제 대중교통 경로나 운임을 확보한 것으로 간주하지 않는다. 조회 기능별 지원 여부를 표시한다. 외부 지도 열기는 명시적인 사용자 동작으로 제공한다. 다운로드한 일정·좌표와 지도 타일은 별개이며, 지도 오프라인 저장은 제공자 허용 범위가 확인될 때 도입한다.

### FR-10 금액 세부 정책

예산은 여행 기준 통화로 정한다. 지출은 원금액·원통화와 적용 환율을 저장한다. 실제 원화 결제액을 알고 있다면 환산 추정치 대신 결제액을 기록할 수 있다. 한 지출을 예상 비용과 실제 지출에 동시에 합산하지 않는다. 환불은 원지출에 연결된 별도 기록으로 남기고 순지출을 계산한다. 결제 완료와 앱의 지출 기록은 다른 개념이다.

### FR-16 추천 세부 정책

초기 추천은 규칙·필터 방식으로 제안한다. 사용자가 선택한 예산, 기간, 계절, 관심 활동을 이용하되 자료가 없는 항목을 추정 사실로 채우지 않는다. ‘유행 여행지’는 최신 지표가 있을 때만 사용한다. LLM 자동 일정 생성은 추가 선택지이며 핵심 기능의 전제조건이 아니다.

## 5. 화면 및 정보 구조

모바일 하단 메뉴를 **홈 / 여행 / 탐색 / 기록 / 설정**으로 제안한다. 여행 상세에서는 **일정·지도 / 준비 / 예약·서류 / 예산 / 기록**을 보여준다. 현재 선택한 여행 이름을 계속 표시하여 다른 여행에 잘못 기록하는 일을 줄인다.

| 화면 | 첫 화면에서 보여줄 내용 | 주요 행동 |
|---|---|---|
| 홈 | 다음 여행, 오늘 일정, 임박한 준비, 마지막 동기화 | 여행 열기, 빠른 지출 기록 |
| 여행 목록 | 예정·진행·지난 여행, 기간·지역 | 새 여행, 보관 |
| 여행 상세 | 날짜와 핵심 요약, 영역별 진입 | 일정·예약·준비물 추가 |
| 일정 | 날짜별 타임라인, 현지 시각, 이동 정보 | 순서 변경, 지도 보기 |
| 준비 | 미완료·완료, 예약 확인과 짐 구분 | 체크, 추천 목록 추가 |
| 서류 | 예약별 파일, 다운로드 상태 | 저장, 미리보기, 연결 |
| 예산 | 기준 통화 예산, 순지출, 미환산 건수 | 지출·환불·환율 입력 |
| 동기화 문제 | 저장된 내 변경과 서버 변경 | 비교 후 선택, 나중에 처리 |
| 탐색 | 검색 조건, 결과, 출처 | 찜, 여행에 추가 |

모든 조회 화면은 빈 상태·불러오는 중·오류·오프라인·오래된 데이터 상태를 구분한다. 입력 오류가 나도 작성 중인 내용은 유지한다. 작은 화면에서 모든 정보를 한 화면에 압축하기보다는 핵심 요약과 상세 진입을 일관되게 제공한다.

## 7. 단계별 개발과 완료 기준

### A. 앱으로 첫 통합 흐름 확보

Android·iOS에서 로그인 → 여행 생성 → 일정·체크리스트·지출·수동 예약·파일 저장 → 서버 재조회가 연결되어야 한다. 기본 로컬 조회 캐시를 둔다. 완료 증거는 두 플랫폼 시연과 서버 영속성 검사다.

### B. 여행 중 사용할 수 있는 앱

오프라인 편집, 다운로드 서류, 충돌 처리, 로컬 알림, 기록·찜·백업을 완성한다. 비행기 모드에서 앱을 재시작하고 편집한 뒤 연결을 복구하는 시나리오가 통과해야 한다. 이 단계까지가 외부 공급사 계약에 의존하지 않는 대학 발표용 핵심 시연 후보이다.

### C. 실제 외부 정보 연결

지도·길찾기·항공·숙소·Gmail·환율을 서비스별로 연결한다. 계약, 비용, 데이터 저장 조건, 테스트 환경을 확인한 기능부터 활성화한다. 연동 확인이 되지 않은 기능도 목표와 요구사항에 계속 남겨둔다.

### D. 실제 거래 흐름

내부 예약·결제·취소를 공급사 테스트 환경에서 검증하고 운영 조건을 충족한 뒤 제공한다. ‘수동으로 기록한 예약’과 ‘앱을 통해 실제 성립한 예약’의 출처를 구분한다.

기간은 개발 인원·발표일을 모르는 상태에서 확정하지 않는다. 각 단계는 사용할 수 있는 결과를 남기며, 발표 시점에 실제 검증된 범위를 보여준다.

## 8. 제품 검증 계획

먼저 소유자의 실제 여행 준비 자료로 필요한 필드를 점검한다. 이후 가능하면 여행 경험자 3~5명에게 ‘예약서 찾기, 준비 상태 확인, 외화 지출 입력’ 과제를 부탁한다. 이는 제안 표본이며 아직 수행한 조사가 아니다. 성공률·소요 시간·입력 오류·헷갈린 문구를 기록한다.

최종 인수에는 다음을 포함한다: 날짜 오류, 시차 및 DST, 환율 누락, 중복 저장, 네트워크 단절, 같은 항목 양쪽 기기 수정, 다른 기기에서 삭제, 손상된 파일, 만료된 세션, 알림 거부, 잘못된 백업 복원. 기능별 인수 결과는 FR ID와 연결한다.

## 9. 추가로 보완한 요구사항

기존 기획에 불명확했던 여러 도시·시간대, 환불 및 환산 기준, 데이터 충돌, 외부 가격 유효시간, 서버 작업 재시도, 파일 오프라인 상태, 개인정보 포함 백업, 알림 권한 거부, 공개 배포 여부를 명시했다. 개발 시작 전 반드시 확인할 것은 실제 테스트 기기와 호환 버전 조합이며, 발표일·시간이 정해지면 단계와 원고 길이를 조정한다.

## 10. 검토 후 보완한 제품 동작

백업 복원은 소유자의 여행·첨부파일 전체 교체를 기본으로 한다. 교체 대상·현재 데이터 건수를 보여주고 확인받으며, 복원 직전 데이터를 별도로 백업한다. 선택 여행을 추가하는 ‘가져오기’는 구분된 기능으로 설계한다.

앱 전환 완료 후에는 앱을 편집의 기준으로 제안한다. 기존 웹은 전환 안정화 기간에 조회용으로 두고, 웹·앱 동시 편집이 필요하면 기존 API에도 버전·변경 로그를 적용한다. 실제 전환 전까지 기존 자료는 모두 보존 대상으로 취급한다. 이는 설계 기본안이며 현재 웹을 변경한 것은 아니다.

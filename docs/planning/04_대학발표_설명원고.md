# 개인 여행 공간 — 대학 발표용 설명 원고

작성일: 2026-11-01 · PPTX 제작 전 단계의 원고 · 발표 시간 미정

## 1. 발표 제목

**Kotlin Multiplatform을 활용한 오프라인 지원 개인 여행 관리 앱 설계**

부제: 여행 일정·예약 서류·준비물·지출을 하나의 여행 단위로 연결하기

현재 문서는 기획·설계 발표를 기준으로 한다. 구현 발표로 전환할 때는 실제 동작 화면과 측정 결과를 추가하고, 완료되지 않은 기능을 완료한 것으로 말하지 않는다.

## 2. 발표의 핵심 문장

“이 프로젝트는 여행자가 여러 곳에 흩어 놓은 일정, 예약서, 준비물, 지출을 하나의 앱에서 관리하고, 인터넷 연결이 불안정한 상황에서도 저장한 정보를 사용할 수 있도록 만드는 프로젝트입니다.”

## 3. 설명 순서와 원고

### 문제와 대상

여행 준비에서는 일정은 메모장, 예약서는 이메일, 장소는 지도, 비용은 별도 기록에 흩어질 수 있습니다. 저는 개인 여행을 기준으로 이 자료를 여행 단위로 묶고, 현지에서 필요한 정보를 빠르게 찾을 수 있도록 설계했습니다. 이 문제의 빈도와 효과는 사용자 과제로 검증할 계획이며, 아직 조사 통계가 있는 것은 아닙니다.

### 해결 방법

앱에서 여행을 만든 뒤 일정, 준비물, 예약과 서류, 예산을 연결합니다. 출발 전에 필요한 서류를 다운로드하고, 현지에서 오프라인으로 지출과 기록을 작성합니다. 연결이 돌아오면 서버에 반영하고 다른 기기에서도 확인합니다.

### 왜 앱인가

여행 중에는 휴대전화로 예약서를 꺼내 보거나 사진과 지출을 바로 기록하는 흐름이 중요합니다. 따라서 모바일 앱을 주 사용 환경으로 정했습니다. 파일 선택, 알림, 기기 저장소 같은 OS 기능도 사용합니다.

### 왜 Kotlin Multiplatform인가

Android와 iOS에서 같은 여행 규칙을 따르게 하려면 날짜 검증, 금액 처리, 저장과 동기화 규칙을 일관되게 관리해야 합니다. Kotlin Multiplatform으로 공통 로직을 공유하고 Compose Multiplatform으로 화면도 공유하도록 설계했습니다. 지도와 보안 저장소처럼 OS가 다른 부분은 별도 구현합니다. 모든 코드가 자동으로 공유된다는 뜻은 아닙니다.

### 왜 백엔드가 필요한가

기기 안에만 저장하면 휴대전화를 바꾸거나 다른 기기에서 같은 여행을 이어 보기 어렵습니다. Spring Boot 서버는 인증, 중앙 데이터 저장, 동기화, 외부 서비스 연결을 담당합니다. PostgreSQL은 여행·예약·지출의 관계와 변경을 일관되게 저장합니다. 로컬 DB와 서버 DB는 서로 다른 역할을 가집니다.

### 가장 중요한 설계 문제

인터넷이 끊긴 동안 두 기기에서 같은 일정을 수정하면 충돌이 생깁니다. 마지막으로 도착한 내용을 무조건 저장하면 먼저 작성한 내용을 잃을 수 있습니다. 따라서 레코드 버전과 작업 ID를 사용해 충돌과 중복 요청을 구분하고, 충돌 시 사용자가 두 내용을 비교하도록 설계했습니다.

금액은 통화와 환율을 함께 저장합니다. 환율이 없는 지출을 0원으로 합산하지 않습니다. 항공편은 출발과 도착의 시간대가 다르므로 각각의 시간대와 실제 시점을 저장합니다.

### 외부 연동과 확장

항공권·숙소 검색과 내부 예약·결제·취소도 전체 목표에 포함합니다. 다만 공급사 권한과 API 계약이 필요하므로 직접 기록하는 관리 기능부터 완성하고 연동을 확장하는 구조입니다. 추천 기능은 먼저 출처와 이유를 설명할 수 있는 필터·규칙 방식으로 설계했습니다.

### 검증과 기대 효과

검증할 핵심은 ‘여행 생성부터 저장까지 연결되는가’, ‘앱과 서버를 다시 켜도 데이터가 남는가’, ‘오프라인에서 예약서를 열 수 있는가’, ‘재연결 후 데이터가 중복되거나 사라지지 않는가’입니다. 사용성 측면에서는 예약서 찾기 시간과 과제 성공률을 비교할 계획입니다. 기대 효과와 실제 측정 결과는 구분해서 제시합니다.

## 4. 구현 후 사용할 시연 시나리오

아래는 시연 계획이며 현재 앱이 구현되었다는 의미가 아니다.

1. 가상 여행 ‘오사카 3박 4일’을 생성한다.
2. 일정과 준비물을 추가하고 하나를 완료한다.
3. 가상 예약 내역과 시연용 PDF를 연결한다.
4. 여행 자료 다운로드 완료를 확인한다.
5. 비행기 모드에서 앱을 종료·재실행해 PDF를 연다.
6. 지출과 메모를 작성하고 미동기화 표시를 확인한다.
7. 네트워크를 복구해 서버 반영과 다른 기기 조회를 보여준다.
8. 시간이 허용되면 같은 일정의 수정 충돌을 보여준다.

실제 예약번호·여권·결제 정보는 시연에 사용하지 않는다. 대학 네트워크 상태에 대비해 실행 가능한 로컬 서버 구성과 사전 녹화 시연을 준비할 수 있다. 사전 녹화는 녹화임을 밝힌다.

## 5. 예상 질문과 답변

**Q. 기존 여행 앱과 다른 점은 무엇인가요?**

개인 여행의 일정·서류·준비·지출을 연결하고 오프라인 사용과 기기 간 데이터 일관성에 초점을 맞췄습니다. 시장 최초라는 주장은 하지 않으며, 기존 서비스와의 구체적 기능 비교 및 사용성 검증이 필요합니다.

**Q. KMP와 Compose는 같은 건가요?**

KMP는 공통 Kotlin 코드를 여러 플랫폼에서 사용하도록 하는 기반이고, Compose Multiplatform은 UI를 공유하는 프레임워크입니다. KMP를 사용하면서 iOS UI를 SwiftUI로 만들 수도 있지만 이번에는 공통 UI를 선택했습니다.

**Q. Flutter 대신 KMP를 선택한 이유는요?**

Kotlin 중심으로 앱과 서버를 개발하고 공통 업무 로직을 관리하려는 방향 때문입니다. Flutter도 적합한 대안이며 성능이 더 나쁘다고 판단한 것은 아닙니다.

**Q. Windows에서 iOS까지 개발할 수 있나요?**

Windows에서 공통 코드와 Android·서버 작업을 진행할 수 있지만 iOS 빌드와 검증에는 macOS와 Xcode 환경을 사용합니다.

**Q. 오프라인이면 로그인 검증은 어떻게 하나요?**

최초 로그인과 서버 인증은 온라인에서 수행합니다. 이미 기기에 저장된 여행 자료는 오프라인에서 사용할 수 있게 하고 기기 보안과 앱 잠금으로 보호합니다. 서버 세션 폐기는 오프라인 기기에 즉시 전달되지 않는다는 경계가 있습니다.

**Q. 로컬 DB와 서버 DB를 둘 다 쓰면 데이터가 꼬이지 않나요?**

그 위험을 줄이기 위해 로컬 변경 큐, 고유 작업 ID, 서버 버전, 변경 커서를 사용합니다. 충돌을 감지하고 해결하는 흐름을 별도로 검증합니다.

**Q. AI 추천이 반드시 필요한가요?**

아닙니다. 핵심은 신뢰할 수 있는 여행 관리입니다. 먼저 날짜·예산·취향을 바탕으로 설명 가능한 추천을 만들고, AI는 실제 필요와 데이터 품질을 확인한 뒤 추가할 수 있습니다.

**Q. 실제 예약과 결제까지 되나요?**

전체 목표에 포함되어 있지만 현재는 설계 단계입니다. 공급사 권한과 테스트를 충족해야 구현 완료라고 말할 수 있습니다. 직접 입력한 예약 기록을 실제 거래로 표현하지 않습니다.

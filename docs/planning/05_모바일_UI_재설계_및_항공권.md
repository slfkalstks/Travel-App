# 모바일 UI 최종 재설계 · 항공권 연결

작성일 2026-11-01. 기존 문서의 화면 구성·색상·시연 표기와 충돌하면 이 문서와 최종 [DESIGN.md](../../DESIGN.md)가 우선한다. 현재 단계의 UI/UX를 먼저 검수한 뒤 문서를 실제 구현에 맞췄다.

## 사용자 요구와 최종 디자인

Android·iOS용 Kotlin Multiplatform 앱을 유지하며, 기존 베이지·러스트·세리프 화면과 중간 단계의 흰색·파란색 화면을 라임·잉크 방향으로 전면 변경했다. ‘더 젊고 경쾌하게’라는 요구를 선명한 색면, 굵은 제목, 둥근 카드, 티켓형 일정, 캡슐 하단 메뉴, 짧은 눌림 반응으로 구체화했다. 특정 연령층 전체의 취향을 검증했다는 뜻은 아니다.

- 강조 Signal `#D7FF4F`, 잉크 `#181B17`, 바탕 `#FAFBF6`, 그룹 `#EFF1E8`, 밝은 화면의 의미 강조 `#365300`.
- 기본 그룹 반경 24dp, 강조 카드 26dp, 버튼·달력 입력 18dp. Noto Sans KR의 굵은 제목과 읽기 쉬운 본문 사용.
- 목적지 이름은 ‘오사카 여행’. 출발 카운트다운·준비 완료율·박수·지출 합계는 데이터에서 계산.
- 사용자 화면에 샘플·더미·프리뷰 배너를 반복하지 않음. 초기 데이터·실제 연결 범위는 개발 문서에서 관리.
- 가짜 실시간 가격·예약 확정·사용자 수·추천 순위를 만들지 않음.

## 화면 구조

| 영역 | 구성 |
|---|---|
| 최상위 | 여행 / 항공권 / 장소 / 기록의 네 탭 |
| 하단 메뉴 | 잉크 캡슐, 라임 선택 면, 아이콘과 짧은 라벨 |
| 설정 | 상단 버튼; 다크 모드·동작 줄이기·새로고침 |
| 여행 홈 | 사진이 있는 잉크 여행 카드, 준비 상태, 라임 항공권 카드, 첫날 일정, 경비 |
| 여행 상세 | 일정 / 준비물 / 예약 / 경비 |
| 편집 | 일정·지출·메모 작성, 일정 전체 수정, 준비 항목 추가·수정; 고정 헤더와 키보드 위 저장 버튼 |
| 장소 | 검색·분류·저장/해제·Google 지도 외부 이동 |

현재 단일 여행 데이터를 다루며 여행 생성/삭제·장소의 일정 직접 추가·예약 편집을 완료 기능으로 소개하지 않는다. 메모는 전체 본문을 카드에서 읽을 수 있다.

## 항공권 인수 조건과 현재 범위

1. 현재 제공하는 공항 목록에서 출발·도착을 선택하고 서로 바꾼다.
2. 왕복·편도를 선택한다. 편도 URL에는 반환일을 포함하지 않는다.
3. 달력과 직접 입력으로 날짜를 선택한다. 존재하는 날짜·왕복 순서·서로 다른 공항을 검증한다.
4. 항공권 보기 버튼은 노선·날짜를 Google 항공편 URL 검색어로 전달한다.
5. 현재 안내 인원은 성인 1명·일반석이다. 인원·좌석 변경은 제공자 화면에서 한다.
6. URL을 열지 못하면 같은 화면에 오류를 보여준다. 외부 검색 이동을 예약 성공으로 처리하지 않는다.
7. 앱 내부 운임 API·예약·결제는 없다. 공개 URL의 자연어 해석과 제공자 화면 변경 가능성을 별도 기술 검증에서 관리한다.

항공권 화면은 큰 소개 문구를 제거하고 노선을 가로로 배치했다. iOS 캡처에서는 날짜·CTA·외부 제공자 설명까지 첫 화면에 보인다. 스크롤 기능은 작은 화면과 큰 글꼴에 대비해 유지한다.

## 실제 UI 구조와 기술 판단

`TravelApp`이 페이지·상세 탭·설정·편집 상태를 관리하고, 화면별 UI는 공통 Compose 소스의 HomeScreen, TripScreen, FlightScreen, OtherScreens로 나뉜다. DesignSystem은 테마·그룹·버튼·탭·달력 입력을 제공한다. 이름이 EditorDialog인 편집 컴포넌트는 현재 일반 전체 화면 Compose 레이아웃이며, 편집 중 기존 화면과 하단 메뉴를 숨긴다.

최상위 페이지는 SaveableStateHolder와 rememberSaveable로 검색 조건 등을 보존한다. 선택 날짜는 상세 화면 상위 상태로 올려 내부 탭 전환에도 유지한다. 설정 복귀 경로와 상세 뒤로가기를 구분하며 편집기는 자체 뒤로가기를 처리한다.

KMP 공통 UI와 Kotlin 백엔드는 유지한다. 색상·레이아웃 변경 때문에 API·저장 규칙·중복 요청 방지 구조를 교체하지 않는다. 외부 링크는 Compose LocalUriHandler를 사용하고 http(s) URL만 허용한다. 웹뷰나 항공권 공급사 SDK를 새로 도입하지 않았다.

선명한 라임은 버튼·선택·주요 노선 면에 쓰고 작은 링크에는 진한 녹색을 사용해 가독성을 유지한다. 버튼은 눌림 시 0.98배로 반응하고 앱의 ‘동작 줄이기’에서는 스케일·화면 전환을 제거한다.

## 검수와 발표 자료

실제 iOS 시뮬레이터 화면으로 홈·일정·항공권·다크 모드를 검토했다. 소프트웨어 키보드가 있는 오류 입력 화면에서 상단 유지, 입력 포커스, 키보드 위 저장 버튼 위치를 확인했다. 전체 크기·접근성 보조기술·실물 기기 검증을 모두 완료했다는 의미는 아니다.

화면 캡처와 설명은 문서로 보관한다. PPTX는 사용자가 따로 요청하기 전까지 생성하지 않는다. 저장소 게시·빌드 결과는 README와 별도 검증 기록에서 관리하며 이 문서는 UI 검수·설계 범위를 설명한다.

## 디자인 자료 적용

[재설계 리뷰](../redesign-review.md)에는 MengTo·Taste·Vercel·VoltAgent·ECC·21st의 실제 사용 범위를 기록했다. 21st는 설치된 지침을 적용했지만 원격 기능은 인증되지 않았고 Kotlin 검사 대상이 0개였던 결과를 통과 근거로 쓰지 않는다. Taste 추출 자료는 중간 구조 참고이며 최종 라임 디자인 전체가 자동 생성·검증되었다고 표현하지 않는다.

## 항공 상세 정보 정리

노선은 제목에서 한 번 표시한다. 일정의 항공 카드와 상세에서 같은 출발지·도착지를 장소 설명으로 다시 반복하지 않는다. 일정 상세는 날짜와 출발·도착 시간을 한 줄로 묶고 사용자가 기록한 메모를 별도로 표시한다. 예약 항공 상세는 제목, 날짜·출발 시각, 선택·확정 상태와 존재하는 예약번호만 표시한다. 예약 데이터에 도착 시각 필드가 없으므로 임의의 값을 만들어 넣지 않는다.

## 일정 카드와 메모 편집

날짜 선택 카드는 위에 작은 날짜, 아래에 큰 ‘1일차’를 표시한다. 각 일정 카드에는 저장한 메모를 최대 두 줄까지 보여준다. 카드를 누르면 전체 화면 일정 상세가 열리며 메모 전체를 읽고 수정할 수 있다. 최대 2,000자, 빈 값 저장으로 메모 삭제, 저장 중 입력 잠금, 오류 시 입력 유지, 성공 후 카드 반영을 지원한다. PATCH `/api/demo/events/{id}/note`는 전체 workspace를 반환한다.

## 일정 전체 수정·삭제와 준비 항목 관리

이번 확장은 프런트엔드 화면·입력 검증·삭제 확인을 먼저 구성한 다음 서버 저장 기능에 연결했다. 새 기능의 빌드·테스트·기기 검증 결과는 별도 구현 검증 기록에서 관리한다. 이전 캡처만으로 새 기능이 모두 검증되었다고 표현하지 않는다.

일정 상세의 ‘일정 수정’은 `event-edit|id` 경로로 기존 날짜·시작/종료 시각·제목·카테고리·장소·메모를 미리 채운다. 상세에 저장하지 않은 메모가 있으면 ‘메모 저장 후 일정 수정’으로 먼저 저장하며, 실패 시 이동하지 않는다. `EventEditInput`은 편집 가능한 일곱 필드만 전송한다. 예상 비용·위도·경도는 서버에서 기존 값을 보존한다. 제목·날짜·여행 기간·시각 순서·장소·메모 길이를 검증하고 오류 시 입력을 유지한다.

일정 삭제 확인에는 일정명·날짜·시간과 메모도 함께 삭제된다는 설명을 표시한다. 확인 전에는 삭제하지 않는다. 처리 중 중복 요청·닫기를 막고, 실패는 확인창 안에서 알려준다.

준비 항목은 목록에서 추가하거나 항목별 수정 행동으로 연다. `TaskEditorScreen`은 이름과 ‘준비물/예약 확인’ 분류를 입력받는다. 수정에는 기존 값을 채우고 `TaskInput`으로 이름·분류만 전송해 기존 완료 상태를 보존한다. 삭제는 수정 화면에서 시작해 항목 이름을 확인한다. 저장·삭제 실패 시 편집 화면의 입력을 유지한다. 목록과 홈의 완료 수·남은 수·진행률은 반환된 목록에서 다시 계산한다.

여기서 구현한 관리는 한 여행 안의 일정·준비 항목이다. 여행 자체의 생성·수정·삭제, 다중 여행 관리, 예약 편집까지 완료했다는 의미는 아니다.

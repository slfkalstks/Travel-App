## 2. Kotlin Multiplatform을 선택하는 이유

KMP는 Android와 iOS에 같은 프로그램 파일을 그대로 배포하는 기술이 아니다. 공통 Kotlin 소스에서 각 플랫폼에 맞는 결과물을 빌드하고, 플랫폼 전용 기능은 각 구현을 연결한다. Compose Multiplatform은 그 위에서 화면도 공유할 수 있게 하는 별도 UI 계층이다.

공식 지원표에서 KMP와 Compose의 Android·iOS는 Stable로 표시되어 있다. 이는 프레임워크 지원 상태이며 우리 앱의 지도·파일·알림이 자동 검증된다는 뜻은 아니다. [지원 상태](https://kotlinlang.org/docs/multiplatform/supported-platforms.html)

| 선택지 | 장점 | 이 프로젝트에서의 비용·판단 |
|---|---|---|
| **KMP + Compose 공통 UI** | Kotlin 로직과 화면을 함께 관리 | 플랫폼별 SDK 연결·iOS 검증 필요. 이번 선택 |
| KMP 로직 + Android Compose / iOS SwiftUI | 공통 업무 로직과 각 OS 화면 특성 양립 | 화면을 두 벌 작성해야 함. iOS 전용 UX 비중이 커지면 재검토 |
| Kotlin Android + Swift iOS 별도 개발 | 플랫폼 기능과 UI를 직접 제어 | 일정·금액·검증 로직도 중복 관리하기 쉬움 |
| Flutter | Dart로 공통 UI·로직 구성 가능 | 유효한 대안이나 Kotlin 사용 방향과 다른 언어를 추가해야 함 |
| React Native | React 경험과 TypeScript 일부 로직 활용 가능 | 기존 웹 DOM·CSS를 그대로 앱 화면으로 재사용할 수는 없음; 이번 Kotlin 선택과 다름 |
| React PWA 유지 | 기존 구현 활용도가 가장 높음 | 사용자가 요청한 네이티브 앱 중심 방향과 달라 이번 주력 경로로 선택하지 않음 |

성능 우열이나 생산성 배수를 실측 없이 주장하지 않는다. 선택 이유는 ‘Kotlin 중심 개발, 두 모바일 OS, 여행 화면의 공통성’이다. Flutter·React Native도 가능한 대안이며 잘못된 선택으로 평가하지 않는다. [Flutter 구조](https://docs.flutter.dev/resources/architectural-overview), [React Native 구조](https://reactnative.dev/architecture/overview)

## 3. Compose와 플랫폼 기능의 경계

일정·예산·체크리스트 등은 공통 UI로 만든다. 지도, 카메라·문서 선택, 알림, 보안 저장소는 플랫폼별 어댑터를 둔다. Compose는 UIKit과 상호 삽입할 수 있으므로 iOS 네이티브 뷰가 필요한 화면을 연결하는 기반이 있다. 실제 SDK 연동은 별도 검증한다. [UIKit 통합](https://kotlinlang.org/docs/multiplatform/compose-uikit-integration.html)

전체 화면을 네이티브로 만들면 OS별 조정에는 유리하지만 유지할 화면이 늘어난다. 반대로 모든 기능을 억지로 공통화하면 SDK 문제가 생길 때 해결이 어려워진다. 따라서 공통으로 의미가 같은 부분을 공유하고, OS 동작이 다른 기능은 경계를 명시한다. 코드 공유율을 목표 숫자로 먼저 정하지 않고 결과로 측정한다.

## 4. ViewModel·Coroutines·StateFlow

일정을 불러오는 동안 사용자가 화면을 이동하거나, 오프라인 저장 후 동기화 결과가 도착하는 상황을 처리해야 한다. ViewModel에 화면 상태를 모으고 Coroutines로 비동기 작업의 수명과 취소를 관리하며 StateFlow로 상태를 전달한다. 코루틴은 비동기 작업을 표현하는 Kotlin 라이브러리 기반 기능이다. [Coroutines](https://kotlinlang.org/docs/coroutines-overview.html)

콜백 중심 구현보다 저장·조회 흐름을 순서대로 읽기 쉽다는 것이 선택 판단이다. Rx 계열도 가능하지만 별도 개념 체계를 추가할 필요가 적다. 완전한 MVI 프레임워크는 초기 화면 규모에 비해 구조가 커질 수 있어, 상태와 이벤트의 단방향 흐름만 적용한다. 복잡한 상태 전이가 늘면 전용 상태 머신을 도입한다.

## 5. Ktor Client·JSON·의존성 주입

Ktor Client는 Android와 iOS 등 KMP 타깃을 지원한다. 공통 요청 규칙을 두고 Android와 iOS에 맞는 엔진을 설정한다. 플랫폼별 네트워크 라이브러리만 사용할 때보다 인증·오류·재시도 로직의 중복을 줄일 수 있다는 판단이다. [Ktor 지원 플랫폼](https://ktor.io/docs/client-supported-platforms.html)

앱 JSON은 kotlinx.serialization을 사용한다. JVM·Native를 지원하므로 공통 DTO에 적합하다. 서버는 Spring의 기본 직렬화 구성과 Kotlin 지원을 활용하며, 앱과 서버가 반드시 같은 직렬화 라이브러리를 써야 하는 것은 아니다. OpenAPI와 실제 JSON 계약이 같아야 한다. [Kotlin 직렬화](https://kotlinlang.org/docs/serialization.html)

의존성은 생성자 주입으로 명시하고 앱 시작점에서 조립한다. Koin 같은 DI 프레임워크는 구성 규모가 커지면 검토한다. 수동 DI는 프레임워크 학습 부담이 작지만 연결 코드가 늘어날 수 있다는 비용이 있다.

## 6. Room KMP·SQLite 대안 비교

| 대안 | 특징 | 판단 |
|---|---|---|
| **Room KMP + SQLite** | DAO·스키마·SQLite 기반 저장, KMP 공식 안내 | 여행 데이터·Outbox 트랜잭션에 적합한 기본안 |
| SQLDelight | SQL 중심으로 타입 안전한 접근 코드 생성 | SQL을 직접 통제하고 싶을 때 좋은 대안 |
| JSON 파일 | 작은 설정 저장에 단순 | 관계·검색·부분 수정·동시 쓰기·마이그레이션 부담이 커 주요 데이터에는 부적합 |
| 서버만 사용 | 로컬 저장 설계가 단순 | 통신 불안정 상황의 요구를 충족하지 못함 |

Room이 서버 동기화를 자동 해결해 주지는 않는다. 충돌·중복·삭제·커서는 별도 구현한다. SQLite DB가 자동으로 암호화되는 것도 아니므로 기기 저장 보호 정책을 따로 설계한다. Room에서 필요한 KMP API와 안정 버전의 호환성을 스파이크로 확인하고, 문제가 있으면 SQLDelight를 대체 후보로 삼는다. [Room KMP](https://developer.android.com/kotlin/multiplatform/room), [SQLDelight](https://sqldelight.github.io/sqldelight/)

## 7. Kotlin + Spring Boot 대안 비교

| 대안 | 장점 | 이번 판단 |
|---|---|---|
| **Spring Boot MVC** | 인증·검증·데이터 접근·트랜잭션을 통합하고 기존 코드 활용 | 기존 Spring 요구 유지, 관계형 CRUD·파일·외부 연동에 적합 |
| Ktor Server | Kotlin 중심으로 필요한 기능을 구성 | 유효한 경량 대안이나 기존 서버를 교체할 이득이 아직 입증되지 않음 |
| NestJS | TypeScript 서버 구조와 도구 활용 | React 중심일 때 언어 통일 장점이 컸으나 이번에는 Kotlin 중심 |
| Firebase/Supabase 중심 | 관리형 기능으로 시작 비용을 줄일 여지 | 기능별 제약·비용·결합도를 따져야 하며 직접 서버 설계 학습 목표와 다름 |

Spring Boot는 공식 Kotlin 지원을 제공한다. [Kotlin 지원](https://docs.spring.io/spring-boot/reference/features/kotlin.html)

JPA를 쓰는 일반 요청은 MVC 방식으로 구성한다. WebFlux를 도입한다고 자동으로 빨라지는 것은 아니고, 블로킹 JPA와 혼합 시 실행 모델을 추가로 관리해야 한다. 초기에는 동작과 트랜잭션이 명확한 구성을 선택한다. 오래 걸리는 가져오기·백업은 작업 상태를 반환하고 서버 작업으로 수행한다.

## 8. JPA·PostgreSQL·Flyway

JPA는 여행과 그 하위 데이터의 CRUD·관계·버전 필드 처리에 활용한다. SQL을 세밀하게 제어하는 jOOQ·Exposed·JDBC도 대안이다. 대량 집계와 변경 로그 조회는 필요한 경우 명시적 SQL을 사용한다. JPA 엔티티를 API 응답으로 직접 노출하지 않으며 N+1 조회·지연 로딩·Kotlin 클래스 프록시 설정을 점검한다.

PostgreSQL은 여행→예약→파일, 여행→지출→환불처럼 관계가 명확한 데이터를 트랜잭션으로 다루기 위한 선택이다. MySQL/MariaDB도 이 요구를 충족할 수 있고, 본 프로젝트에서는 기존 PostgreSQL 자산과 정밀 수치·관계형 일관성을 유지하는 이점이 있다. MongoDB가 불가능해서 제외하는 것이 아니라 현재 모델이 관계 중심이기 때문이다. SQLite는 기기 로컬 역할로 사용한다. [정밀 수치 타입](https://www.postgresql.org/docs/current/datatype-numeric.html)

Flyway를 통해 SQL 변경 이력을 순서대로 적용한다. Liquibase도 대안이지만 초기에는 SQL 자체를 읽고 검토하는 방식이 단순하다. 운영 DB를 ORM의 자동 스키마 수정으로 바꾸지 않는다. 적용한 마이그레이션 파일을 수정하는 대신 새로운 변경 파일을 추가한다. 파괴적 변경 전 백업·변환 검증을 수행한다.

## 9. REST·인증·파일·지도

REST는 여행별 자원 조회와 변경, 동기화 명령을 설명하기 쉽고 기존 API를 확장하기 좋다. GraphQL은 복합 조회 조합에 장점이 있지만 현재 조회 요구에 필수는 아니다. gRPC는 내부 고성능 통신이 필요할 때 검토할 수 있으나 이 프로젝트에서 복잡성을 추가할 이유가 작다.

인증은 개인용 단일 서버에 맞춰 opaque token을 제안한다. JWT는 서비스 간 서명 검증에 유용하지만 즉시 폐기·기기 관리에서는 별도 상태가 필요할 수 있다. opaque token은 서버 조회가 필요한 비용 대신 폐기와 만료를 직접 관리할 수 있다. 비밀번호 저장은 Spring Security의 PasswordEncoder를 사용한다. [공식 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/password-encoder.html)

파일은 DB BLOB 대신 비공개 파일/객체 저장소를 선택해 DB 백업과 대용량 전송 책임을 분리한다. 다만 DB·파일 백업의 일관성을 별도로 보장해야 한다. 구체적인 클라우드 업체와 요금은 아직 결정하지 않았다.

국내 Kakao, 해외 Google 지도는 기존 사용자 선호를 유지한 선택이다. Kakao는 Android/iOS SDK를 안내하고 Google은 플랫폼별 키 제한을 안내한다. 공통 KMP 지도 SDK가 모두 해결해 준다고 가정하지 않는다. 지도 표시·장소 검색·길찾기·오프라인 사용의 이용 조건과 비용을 각각 확인한다. [Kakao 지도](https://developers.kakao.com/docs/ko/kakaomap/common), [Google 키 보안](https://developers.google.com/maps/api-security-best-practices)

## 10. 테스트·빌드·CI

공통 업무 규칙은 kotlin.test, 서버는 JUnit과 실제 PostgreSQL 통합 테스트를 사용한다. PostgreSQL Testcontainers를 사용하면 테스트용 DB를 재현 가능한 방식으로 실행할 수 있지만 컨테이너 실행 환경이 필요하다. 환경이 없으면 별도 테스트 DB를 운영한다. H2 통과만으로 PostgreSQL 호환성을 판단하지 않는다. [Testcontainers PostgreSQL](https://java.testcontainers.org/modules/databases/postgres/)

Android와 iOS는 공통 테스트 외에 각각 실기기에서 지도·알림·파일·오프라인 시작을 검증한다. UI 프레임워크 테스트만으로 OS 기능 검증을 대체하지 않는다.

Gradle wrapper·버전 카탈로그로 빌드를 고정한다. CI는 서버·공통 테스트·Android 빌드를 수행하고, iOS 빌드는 macOS 실행기를 사용한다. GitHub 저장소를 채택하면 GitHub Actions를 제안하되 CI 업체는 아직 확정되지 않았다. Docker Compose는 개발용 서버·DB 환경에 사용하며 Kubernetes는 운영 규모가 요구할 때 재검토한다.

## 11. 버전 확정 절차

Kotlin, Compose, Gradle, Android Gradle Plugin, JDK, Xcode, Ktor, Room/KSP는 상호 호환 조합으로 선정해야 한다. 각 ‘최신 버전’을 독립적으로 고르는 방식은 피한다. 공식 호환표 확인 → Android/iOS 최소 앱 빌드 → DB 읽기/쓰기 → 네트워크·파일·지도 스파이크 → 안정 조합 잠금 순서로 확정한다. 최소 OS 버전도 선택한 SDK의 요구와 실제 기기를 확인한 후 결정한다. [Compose 호환성](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html), [개발 환경](https://kotlinlang.org/docs/multiplatform/quickstart.html)

## 12. 기술 도입을 유보한 항목과 이유

Redis·Kafka·Kubernetes·검색 엔진·벡터 DB·LLM은 현재 핵심 흐름에 필수로 선정하지 않았다. 이는 장기 기능을 배제하는 결정이 아니다. 캐시 필요성, 비동기 작업량, 검색 품질, 추천 요구가 실제 측정으로 드러나면 도입한다. 도구 수보다 여행자 문제와 검증 가능한 결과가 기술 선택의 기준이다.

## 13. 사실 확인 기록

2026-11-01에 공식 문서를 확인했다. KMP/Compose 모바일 지원, Ktor 지원 플랫폼, Room KMP 안내, Spring Kotlin 지원, PostgreSQL 수치 타입, 지도 SDK와 키 제한, 공급사 이용 요건을 확인했다. 외부 API 계정의 실제 권한·사용 요금·토스뱅크 공식 연동 권한은 확보하지 않았다. 시간·비용 절감률, 코드 공유율, 앱 성능 수치는 측정 결과가 없으므로 제시하지 않는다.

## 예약 현지 시각 처리 추가 결정

모바일 공통 코드는 현재 `kotlinx-datetime:0.7.1`에 고정했다. `java.time`만으로 앱을 작성하면 iOS 공통 코드에서 그대로 사용할 수 없고, 플랫폼별 날짜 구현을 따로 두면 같은 예약 검증을 두 번 유지해야 한다. `kotlinx-datetime`의 시간대 ID·로컬 시각·instant 변환을 공유하고, Spring 서버는 JDK `ZoneRules.getValidOffsets`로 gap·overlap과 오프셋을 최종 검증한다. 고정된 `UTC+09:00` 문자열이나 기기의 현재 시간대만 사용하는 방식은 여행지의 날짜별 규칙을 표현하지 못하므로 채택하지 않았다. [Kotlin TimeZone API](https://kotlinlang.org/api/kotlinx-datetime/kotlinx-datetime/kotlinx.datetime/-time-zone/), [JDK ZoneRules API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/zone/ZoneRules.html#getValidOffsets(java.time.LocalDateTime))

일반 로컬 시각 변환만 호출해 gap을 다른 시각으로 자동 보정하는 동작을 예약 입력 검증에 사용하지 않는다. 공통 구현은 주변 오프셋 후보를 구한 뒤 원래 현지 시각으로 되돌아오는 후보만 허용한다. JVM 테스트는 JDK 규칙의 전환 경계와 독립 비교한다. 각 OS의 시간대 DB는 다를 수 있어 최종 저장 시 서버가 검증하고 오류는 폼 입력을 보존해 표시한다. 실제 검증 수치와 남은 모바일 조합은 [검증 기록](../VERIFICATION.md)을 따른다.
